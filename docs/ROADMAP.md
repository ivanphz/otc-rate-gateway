# otc-rate-suite 迭代路线图

> 本文档回答三个问题：以后要做什么、为什么现在不做、现在预留了哪些接口给以后用。
> 任何 AI 接手迭代前，先读 DESIGN.md 了解现状，再读本文了解方向。**不要超前实现未到阶段的功能。**

## 0. 总蓝图

最终形态是**两个独立项目**协作：

```
otc-rate-suite（本仓库）           ledger（未来独立仓库）
行情 + 报价域                      账务域
─────────────────                ─────────────────
抓盘口、算均价、报价计算            记录每一笔交易(法币↔U、币币)
显示成本浮盈                       自动计算加权成本、库存、利润报表
        │                                ▲
        │  ①读成本: GET /cost 同形状契约   │
        └────────────────────────────────┤
        │  ②推交易: POST 交易事件(契约见§3) │
        └────────────────────────────────┘
```

**为什么拆两个项目**：行情是公开只读数字，账本是交易明细；数据模型(时序快照 vs 复式流水)、存储(KV vs 关系型 D1)、安全等级(可无鉴权 vs 必须鉴权)全都不同。塞进一个仓库违反"改一处不炸另一处"。

**本前端在终局的角色不变**：还是报价计算器，只是成本价的来源从"手工数字"换成"ledger 算出来的数字"，四个模块多一个"推送记账"按钮。**现有架构不需要重构。**

## 1. 阶段划分

### Phase 0（当前，已实现）
- 手工维护单一成本价，存网关 KV(`cost:usdt_cny`)，无鉴权。
- 成本浮盈显示在 卖出U / 代收RMB 两个"U流出"模块。
- 适用前提：一次性大额买入 U，卖完前成本固定。这个前提失效时（恢复高频买入）就是启动 Phase 1 的信号。

### Phase 1：ledger MVP（独立新仓库，不动本仓库）
- 只做 RMB↔USDT 买卖流水：`{时间, 方向, U数量, RMB金额, 备注}`。
- 加权平均成本法计算实时成本 + 库存。
- 存储用 **D1**（流水是关系型数据，KV 不合适）。
- **必须带鉴权**（见 §4 红线）。
- 交付一个接口：`GET /cost` 返回与本仓库 §3.1 完全同形状的数据（`source:"ledger"`）。

### Phase 2：ledger 支持币币交易
- TON/TRX 等多币种、币币兑换的成本链路（例：收 TON 付 USDT，USDT 成本如何结转到 TON）。
- 成本核算方法（加权平均/先进先出）在此阶段定，本仓库不关心。

### Phase 3：前端接入 ledger
- 本仓库改动点只有两处：
  1. config 加开关：成本价来源 `manual`(网关KV) / `ledger`(ledger 的 /cost)。前端读数逻辑不变——这就是 §3.1 契约的意义。
  2. 四个计算模块加"📤 推送记账"按钮，按 §3.2 契约 POST 到 ledger。
- 报表、图表全部在 ledger 侧做，本前端不长胖。

## 2. 现在已经预留的东西（别重复设计）

| 预留 | 位置 | 用途 |
|---|---|---|
| `/cost` 返回体的 `source` 字段 | gateway worker.js | Phase 3 区分 manual/ledger 来源 |
| KV 键名 `cost:usdt_cny` 带币对 | gateway worker.js | 未来多币种成本互不覆盖 |
| 源对象的 `id`/`role` 契约 | 三端 | ledger 若要引用行情源，直接复用 id 体系 |
| `missing_ids` / `node_health` | gateway | ledger 未来若消费行情，可判断数据完整性 |

## 3. 跨项目契约（Phase 1+ 开发 ledger 时照此实现）

### 3.1 成本价供数契约（ledger 必须实现）
```
GET /cost
→ { "cost_price": 6.731, "updated_at": 1783..., "source": "ledger" }
```
说明：Phase 0 的手工模式是"3 组手动点选"（形状见 DESIGN.md 3.3，`{slots, active, source}`）。
ledger 算的是**单一加权成本**，所以 Phase 3 接入时二选一：
- (a) ledger 把加权成本塞进 `slots[0]`、`active=0`，其余两组留给你手工备注；或
- (b) 前端加"成本来源"开关：manual 用 3 组、ledger 用单值 `cost_price`。
无论哪种，前端读数入口只有一个 `getActiveCost()`，改动面很小——这就是把"取成本"收敛成单一函数的意义。

### 3.2 交易事件推送契约（草案，Phase 3 前端实现，Phase 1 ledger 接收）
```
POST /trades
{
  "type": "sell_u" | "buy_u" | "recv_rmb" | "pay_rmb",
  "base": "USDT", "quote": "CNY",
  "base_amount": 1000,      // U 数量
  "quote_amount": 6800,     // RMB 金额
  "rate": 6.80,             // 成交汇率
  "ts": 1783066423811,
  "note": "" 
}
```
字段用全称、不缩写。币币交易的扩展（base/quote 换成任意币种）在 Phase 2 定稿。

## 4. 红线（安全升级触发条件）

1. **无鉴权接口里只许存"单个价格数字"**。任何时候要在网关/ledger 存交易明细、多条记录、金额流水——**先加鉴权再写存储代码**，没有例外。方案届时选：简单 Bearer token（自用够了）或 Cloudflare Access。
2. 隐私基线不动摇：VPS 地址、网关 URL 等继续走"仓库外注入"（CF 变量 / GitHub Variables），ledger 仓库沿用同一套做法。
3. ledger 与本仓库之间**只通过 §3 的两个契约通信**，不共享代码、不共享存储。

## 5. 明确不做的事

- 本前端不做记账 UI、不做流水列表、不做报表。
- 网关不代理 ledger 的写操作（前端直连 ledger，避免网关变成又一个无鉴权写入口）。
- 不为"未来可能的需求"在本仓库加任何空壳代码——预留靠契约文档，不靠死代码。
